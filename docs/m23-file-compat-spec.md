# M23 — SQLite file compatibility: acceptance spec (owner: Research)

Written before Tier 3 reaches milestone 23. Hermes flagged M23 as one of
two budget-blowing risks (with M25); the point of this spec is that "opens a real
SQLite file" gets a written, testable definition instead of an impression,
and that the scope decision (read vs write) is made here, on paper, before
the archaeology starts.

## The claim being tested

MiniDB opens a database file **created by the pinned reference** (SQLite
3.54.0, `sqlite3` CLI, SQLite format 3 as documented in the file format
spec — https://www.sqlite.org/fileformat2.html) and answers queries over
it identically to the reference answering over that same file.

Two decisions baked in:

1. **Read compatibility is the gate.** The ladder says "open a real SQLite
   file" — open means read. Writing SQLite's page format from MiniDB is a
   different and much larger project; if Default wants it in scope, it is
   an explicit expansion recorded before the milestone, not a silent
   discovery inside it. MiniDB writing *its own* file after opening a
   foreign one is likewise out unless stated (see hybrid case below).
2. **Semantic, not byte-level, compatibility.** MiniDB need not lay out
   pages byte-identically; it must read the bytes SQLite laid out. The
   test is always rows-in, rows-out.

## Test corpus (research-authored files, generated by the harness from the
pinned CLI at run time — no checked-in binaries, provenance in the header)

File matrix, each opened by both engines and compared row-for-row:

| # | File content | Exercises |
| --- | --- | --- |
| F1 | one table, 20 rows, INTEGER/TEXT/REAL/NULL mix | basic record format |
| F2 | data on ≥3 pages (rowid B-tree with interior pages) | interior-page traversal |
| F3 | secondary index + composite index, queries that should use them | index reading (plans reported, outcomes compared) |
| F4 | numeric-looking text values (`'5'`, `'3.0'`) | affinity as *stored* by SQLite, read back unmodified |
| F5 | one overflow-sized row (multi-page record) | overflow chain reading |
| F6 | unicode text (é, 汉字) | encoding assumptions |
| F7 | declared `COLLATE NOCASE` column, ORDER BY query | collation from schema text |
| F8 | view + trigger in `sqlite_master`, queries against the view | schema-object reading (scope flag below) |
| F9 | empty table; zero-row file | header-only parse |
| F10 | NULL-heavy column, aggregate over it | NULL representation across formats |

- Query set per file: a fixed handful (full scan, PK lookup, index-using
  WHERE, aggregate) whose expected output is the reference's own answer at
  run time — differential as always, one normalizer.
- **Scope flag for Default:** F8 (views/triggers from a foreign
  `sqlite_master`) may legitimately fail if M23's reading scope stops at
  tables+indexes; it is included so the boundary is *choosable*, not
  accidental. Whatever fails gets classified scope-vs-bug at the review.

## New harness mode (engineer-owned, spec'd here)

The corpus runs each engine on its *own* fresh database; M23 needs one
shared foreign file per case: generate with CLI → open read-only in
MiniDB → open in CLI → compare answers. One tool (`tools/file_compat.py`
or equivalent), same normalizer, same output shape as other tools:

```
FILE-COMPAT F<n>: rows identical  <case detail>   [scope-flag if classified]
M23: <pass-count>/<10>  reference: SQLite 3.54.0  generator: sqlite3 CLI
```

Acceptance: **F1–F7, F9, F10 pass (9/10), F8 classified** (pass, or
explicit scope ruling recorded) — plus the honest report of any file MiniDB
refuses to open, printed as a failure, never skipped.

## What this does NOT claim (state it in the milestone report)

- Not performance on foreign files (benchmark lane, separate).
- Not corruption tolerance (M27's integrity work).
- Not write compatibility (decision 1 above).
- Not cross-version history: files from SQLite versions other than the pin
  are out of scope until someone needs them (a pin bump is a re-baseline
  event anyway).
